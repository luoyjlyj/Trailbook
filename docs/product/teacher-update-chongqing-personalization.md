## 2. 任意重庆游玩地点：最小可交付流程

1. 用户在 App 中选择当前游玩地点，或授权一次前台定位后确认具体重庆 POI。老君洞仅作为说明流程的一个例子；入口、查询、提示词和数据结构均不得固定绑定它。只按地名不能确定同名地点；不在后台连续跟踪。
2. 用户点击“附近推荐”，结合已明确的兴趣、交通方式、剩余时间与饮食/步行限制；缺少关键条件时允许补充。不因为人在寺观游玩而推断宗教信仰等个人属性。
3. 地图服务查询当前位置附近的可用候选地点和必要的交通信息。坐标系、距离和耗时保持数据字典约定，不能由大模型编造。
4. 内容适配层构造“重庆 + 确认后的地点名 + 附近 + 用户兴趣”查询，从实际可用的抖音/小红书渠道获取候选链接。检索内容要区分对当前地点本身的介绍与周边下一站建议；关键词必须由当前确认的 POI 动态构造。
5. 按平台内容 ID 或规范链接去重，筛除错城、无关、失效与超期内容；对当前允许使用的数据集取最多 10 条，记录排序依据和获取时间。
6. 大模型只基于这批证据和地图结果生成结构化推荐：建议先展示 3 个地点及至多 2 个备选，附推荐理由、适合当前条件的原因、来源和信息缺口。数量是建议，候选不足就少展示。
7. 用户查看真实地图与路线，选择收藏或“加入当前行程”；涉及已有锁定和时间冲突时，先展示调整预览，由用户确认。
8. 服务端保存可复用的公共地点线索与来源记录；用户偏好、当前位置和个人推荐历史按用户隔离。下次同区域请求先查未过期记录，再按刷新策略联网更新。

这是实现目标，不是现有 APK 的能力说明。当前 APK 的地图、生成与六类场景仍为预置交互展示；本次仅更新需求文件。

## 3. “前 10 条热门链接”的验收口径

- **推荐解释（A 已确认）**：一次地点相关查询，小红书最多采集 5 条、抖音最多采集 5 条，合并去重后最多 10 条。任一渠道不足 5 条时按实际数量展示，不从另一平台超额补齐；两个平台均无结果则明确显示为空。热门排名范围限于本次查询和实际取得的样本，不声称全平台绝对前十。
- **热门范围**：仅指本次查询条件、平台返回候选集合及明确时间窗口内的排序，不承诺全站“真实前十”。搜索相关性排序、平台热榜和自定义热度排序不是同一件事。
- **排序来源**：平台确有可用热度排序时保留其排序方式；官方没有热门排序但能提供指标时，由项目自行排序。官方接口不可用或无法提供所需内容/指标时，按 A 本次确认采用自行编写网页采集程序的方案获取可访问数据，再按项目规则排序。两个平台指标不直接混算；分别计算平台内热度后再合并。
- **缺少热度证据**：只能显示“相关内容”，不能把搜索前十、搜索引擎摘要或大模型生成链接标为平台热门前十。
- **条数不足**：如仅有 6 条，实际返回 6 条并说明原因，不补造 URL 或重复内容凑数。
- **时效（A 已确认）**：用户主动点刷新后，立即发起新采集请求并绕过普通结果缓存；不等缓存 TTL、不加人为冷却。展示本次刷新和各平台采样时间；正在处理时可见加载状态，同一查询在途时合并重复点击，避免重复请求。上游限速、超时或无权限时显示实际状态和最近一次有效结果，不虚报刚刚刷新成功。普通页面的缓存 TTL 可作为另一条规则单独设定，不阻止用户手动刷新。
- **降级**：无权限、限流、超时、结果为空时，返回明确状态及仍有效的缓存或人工导入内容，并标明来源方式；不得宣称刚刚从平台实时获取。

### 3.1 A 补充确认：官方不提供时自行采集

2026-09-27，A 确认：若官方无法提供所需内容或热门排序数据，则需要自行采集。将网页采集适配器纳入实现计划，不能仅因缺少官方热门接口就自动把需求降为人工粘贴链接。此处“手动爬取”按团队自行编写并按需触发采集程序理解；人工整理继续作为补充。

区分三个情况：官方有排序则记录排序口径；官方无排序但有足够指标则直接自行排名；官方接口不可用或指标不足则研究网页采集。采集本身不产生全平台排名，只能给当前可访问、已采样的候选集合排名。

### 3.2 首版自主排序建议（条数和刷新时效已确认；公式待 POC 冻结）

1. 以当前确认的重庆 POI、周边意图和关键词分别查询小红书与抖音；每个平台最多采集 5 条，合并最多 10 条。先排除错城、无关、失效及重复内容，记录查询关键词、实际条数、来源页面排序和采样时间。遇到一边数量不足不从另一边补额。
2. 在同一平台、同一批次中，根据能稳定获取的点赞、收藏、评论、分享计数计算热度。候选公式为：各指标先做 log(1+计数)，再按该平台本批次同指标最大值归一化到 0～1，最后取所选指标的等权平均。最大值为 0 时该指标记 0。等权是轻量起始建议，不是平台官方算法。
3. 排名所用指标必须对该平台本批次所有入选候选均可获取；某指标缺失时，整批从公式中移除该指标，不把某条缺失值当 0，也不让每条使用不同权重。缩写计数如“1.2 万”保留原显示值并标记近似，不声称精确计数。所有指标都不可用时只能展示相关结果，不生成热度分。
4. 保留原始计数、采样时刻、候选集合 ID、公式版本和计算分；同分时按可用发布时间、最后按稳定内容 ID 排序。时间未知不编造。跨平台不比较原始互动数或归一分。A 已指定两边各采集 5 条；采样不足时不补足另一平台配额。若需展示全局先后顺序，先分别按各自热度排序，再交替取样，标记为项目合并排序，不伪称两个平台统一热度分。
5. 界面使用“本次采集热门内容 Top 10 / 项目排序”等能说明范围的名称，展示获取时间；不足 10 条按实际数量返回。DeepSeek 在这批证据与地图候选中做个性化推荐，用户偏好不能悄悄改写已展示的热度排序。

C/D 优先验证上述各平台 5 条是否可稳定采集、热度指标和发布时间能否读取；再由 A 会签内容时间窗口与公式。手动刷新立即发起请求；上游限速等平台限制如实显示并实测，不以缓存伪装刷新成功。该方案适用于重庆任意确认 POI，不固定老君洞。

新增验收补充：AC-26 覆盖每个平台各 5 条、跨平台合并不超过 10 条、去重、其中一方不足 5 条、不足 10 条、不补额以及自主排序可复算。AC-30 覆盖刷新点击立即发起请求、绕过普通缓存、同一查询合并在途请求；网页结构变化、访问被拒绝及限流时保留状态并如实显示。当前仅更新要求，没有执行网页采集。

## 5. 轻量技术建议

### 5.1 沿用工程并缩小部署范围

采用“Android App → 一个业务 API → 项目数据库”，API 内使用内容、地图和模型三个 Provider 适配器。沿用仓库现有 Node.js/pnpm Monorepo 和 MySQL/Prisma 方向，不因本次要求直接更换数据库或引入另一套客户端框架。

- 一个后端服务负责请求编排、缓存、落库、限流、模型调用和清理任务；模块可分开，部署先不拆微服务。
- 不部署本地大模型；普通开发电脑负责应用与数据库，推理由云端 API 完成。
- 首版先以 POI、关键词、分类和时间索引检索，不预先增加向量库、RAG 平台、Redis、消息队列或全城抓取任务。
- 由用户点击触发查询；对同一公共检索条件合并在途请求，短期缓存复用。公共内容缓存键不包含个人身份；个性化结果必须按用户和条件隔离。
- 缓存新鲜度建议先按 24 小时评估，用户可主动刷新；该值是待验证建议，远短于证据一个月留存上限，二者不混淆。到期证据不得继续作为有效引用。
- API 密钥放服务端环境配置，不写进 APK、HTML、GitHub 或日志。地图客户端 Key 与服务端 Key 分离并按厂商要求限制使用范围。

### 5.2 DeepSeek 型号建议

截至 2026-09-27，建议现阶段正式调用使用 `deepseek-flash`，官方展示版本为 DeepSeek-V4.1-Flash。DeepSeek 官方说明 `deepseek-v4-pro` 的请求当前会路由至 V4.1-Flash 并按 V4.1-Flash 价格计费；V4.1-Pro 尚未上线。因此写 `deepseek-v4-pro` 并不能保证获得独立的 Pro 模型。V4.1-Flash 官方报告为 552B 参数 MoE、输入/输出各 8B/16B 活跃参数，官方公布测试中领先旧 V4-Pro。

这是一项对当前可调用 DeepSeek API 的技术选型建议。“满血版”如果特指未量化/全参数推理或 V4.1-Pro，应等具体 API 上线并由团队重新选型；当前公开信息不能据此承诺云端内部推理精度。

**5.3 单次调用与预算估算（仅模型费）**

- DeepSeek 中国官方价格页记录高峰非缓存输入 ¥2 / 百万 token、输出 ¥8 / 百万 token；闲时价格为高峰价的一半。按一次地点推荐输入 4,000 token（地点、十条短摘要与约束）+ 输出 800 token（结构化推荐），按不享受输入缓存、并发峰值单价保守估算：`4,000 × 2 / 1,000,000 + 800 × 8 / 1,000,000 = ¥0.0144 / 次`，即约 1.44 分。API 返回真实 usage 后以实际用量结算。
- 100 元仅按**DeepSeek 模型调用预算**理解，建议内控上限设 5,000 次标准调用，按上述估算约 ¥72；预留约 ¥28 给较长提示/输出、失败重试和 token 变化。达到额度后暂停模型调用并报告，不自动充值。实际输入输出 token 影响费用，不能保证每次固定价格。
- 上述预算不含高德/地图服务、网页采集运行环境和其他服务费用；若用户所说 100 元涵盖全部新增外部服务，A/D 需另行核价并降低调用上限。
- 适合省钱的常规推荐先用模型默认 `low` 或 `high` effort，POC 比较质量后冻结；没有具体任务需求时不使用 `max`。模型价格会变化，启动 POC 前复核[官方价格页](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)。

### 5.4 API 输出与密钥边界

A 已确认使用 DeepSeek 官方 API，替代此前百炼千问候选。根据 2026-09-27 核对的[DeepSeek 官方价格页](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)和[模型列表](https://api-docs.deepseek.com/zh-cn/api/list-models/)，建议使用当前服务模型 ID `deepseek-flash`，官方接入地址为 `https://api.deepseek.com`。官方当前将 `deepseek-v4-pro` 请求路由到 V4.1-Flash 并按 Flash 价格计费；以实际账号模型列表和 POC 为准，不把别名当作永久固定版本，也不声称服务内部精度或量化方式已验证。

E/D 的交付必须记录：官方接入地址、模型 ID 与实际映射版本、思考模式、结构化输出校验、请求 ID、耗时、输入输出用量和费用。DeepSeek 模型列表会变化，模型 ID 与后端路由在 POC 复核。选择时以实际账号可用列表为准，不能只填写“满血版”。API 能力不等于自动拥有抖音/小红书搜索权限，联网检索与模型推理是两个独立依赖。

模型负责地点线索提取、偏好匹配与解释；确定性规则先过滤错城、饮食硬冲突、营业/时间不可行及步行上限冲突。外部攻略文本作为不可信数据，不能改变系统指令或触发任意工具调用。无效 JSON、虚构来源 ID、未知 POI、与路线数据冲突的输出不得直接入正式推荐。

此前十周 300 元、POC 50 元只是候选预算。新增内容检索和旗舰模型会改变费用，应重新核算每次请求和十周预算；未批准不新增付费订阅或自动充值。

## 6. 入库、复用与一个月留存

A 已确认“本地库”指项目自己管理的数据库。沿用现有 MySQL/Prisma 方向，可在开发电脑运行，部署时随服务迁移；Android 缓存该用户已保存的内容作为配套。公共地点线索在项目数据库中复用，用户偏好、当前位置和推荐历史按用户隔离。

候选实体由 D/E 在 TB-0106 冻结，不在本文直接发布正式接口：

| 记录 | 最小信息 | 复用方式 |
| --- | --- | --- |
| 查询批次 | 重庆 POI、关键词、渠道、排序方法、获取时间、状态、实际条数、缓存标记 | 公共条件相同可复用有效内容；不共享用户精确位置与偏好 |
| 来源证据 | 平台内容 ID、规范链接、标题/允许保存的摘要、发布时间、获取时间、热度及采样时刻、授权/导入方式、到期时间 | 去重并建立版本；不默认保存视频、图片原件和长篇全文 |
| 地点与事实 | 地图 POI ID、名称、城市、坐标及坐标系、类型、事实来源与核验状态 | 多条内容映射到同一 POI；冲突和未知单独记录 |
| 推荐结果 | 所属用户、起点 POI、约束快照、候选与引用 ID、地图结果时刻、模型版本、生成时间、状态 | 保存本人结果；不把 A 用户的推荐原样返回 B 用户 |

沿用一个月来源证据留存要求；具体计算按 Q-06 待确认方案执行，推荐首次保存加一个日历月。相同证据仅被读取或命中缓存不能续期。新抓取形成有独立获取时间的新版本，不借刷新保留旧证据副本。

到期处理应覆盖正文/摘要、缓存、日志中的内容副本、引用和可恢复备份；模型输出若包含可还原的来源内容，也应关联证据期限。已保存行程可保留用户计划本身，但到期来源要失效或脱敏，不能继续展示为可核验依据。独立取得且允许保留的地图 POI 等基础记录按自身数据来源规则管理，不用过期攻略给事实“续命”。
