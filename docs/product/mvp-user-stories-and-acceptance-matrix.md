#### 放行判定

1. **用例通过**：正常变体产生满足已确认约束的结构化结果；边界变体正确区分刚好满足和刚好超限；失败/缺失变体返回可理解、可恢复的结果，保留输入及原计划。预期安全失败算该用例通过。
2. **阻断缺陷（Blocker）**：越权或敏感信息泄露、数据损坏/丢失、关键流程无法继续且无恢复路径。不得带入试点验收。
3. **P0 严重缺陷**：违反硬时间/返程/锁定/明确饮食限制；虚构关键路线或事实并声称已确认；错误读取已到期来源；核心行程被错误覆盖。必须修复并复验，不得带入试点验收。
4. **P1 高优先级缺陷**：六类场景之一或核心闭环不可用、时间线与地图/保存版本不一致、来源审核或降级流程失效，但有明确局部绕行方案。试点验收前必须修复；只有 A 记录影响、绕行步骤、负责人和日期，并由受影响责任成员会签后，才可列为有条件放行。
5. **P2 一般缺陷**：不影响硬约束、数据可信度和核心闭环的视觉/文案/低频体验问题。登记负责人和计划日期后可进入后续迭代。
6. **阶段验收通过**：核心必过与内容可信度必过用例全部通过；无未关闭 Blocker/P0；无未处理 P1（有条件放行项除外）；最小配套用例通过或有 A 记录的不适用依据；真实服务/设备 POC 和环境证据按对应阶段单独达成。任何不适用项须写明理由并由 A 记录，不得直接计为通过。

以上是 A 对验收口径的确认提案。B/C/D/E 会签完成前，范围状态是“提案待团队冻结”；实际用例执行后才可填写通过结论。

## 4. 统一判定规则

以下是供团队评审的验收口径。需要确定数值或具体语义的部分在第 9 节登记，不能用样例参数代替决议。

1. **时间可行**：每天活动、交通和必要缓冲都在可用时间内；活动不重叠；到达下一地点后，至少预留用例规定的转换缓冲再开始活动。停留全过程位于营业窗口内。
2. **起终点完整**：包括起点到首站、站点之间、末站到终点的交通。到达交通枢纽不等于已到酒店；到达酒店不等于已经办理完入住。
3. **硬约束优先**：可用时间、明确饮食禁忌、显式步行上限、锁定项目等先校验，评分不能抵消违反。Q-03 推荐“少走路”显示每日 3000 米/交通单段 800 米的可编辑软目标；用户主动确认“不得超过”才成为硬上限；明确自定义输入始终优先。
4. **锁定语义**：本初稿建议锁定地点、所属日期、开始和结束时间。重排保留这些值及已完成区段；若与新条件冲突，说明冲突并等待用户修改，见 Q-02。
5. **事实可追溯**：交通耗时、距离、营业、天气及餐饮事实来自带来源和更新时间的数据。字段缺失时不能填写零值或让模型编造确定值。
6. **未知与不可行分开**：未知表示缺少判断证据；不可行表示已知约束发生冲突。两者都应说明原因和下一步，不展示为“所有要求已满足”。
7. **结果可用且结构化**：关键状态、时间、地点 ID、路线段、锁定状态、冲突原因和变更摘要可独立读取，页面不需要解析解释文案才能工作。
8. **失败保留原数据**：生成失败保留输入草稿；替换/重排失败保留原行程；保存失败不能提示保存成功。重复提交按同一操作识别，不能产生重复正式计划。
9. **数据一致**：同一行程 ID、版本、日期和站点顺序驱动时间线、地图和保存记录；调整提交成功后共同切换到新版本。
10. **模拟证据分开记录**：Mock 标签、数据版本、模拟服务状态随验收记录保存；真实服务验收另记录供应商、查询时间和设备。

所有验收条目初始执行状态统一为 **未执行**。团队评审状态统一为 **待确认**，不能用“文档已写好”替换上述状态。
