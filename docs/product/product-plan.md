# 城市旅行智能攻略与动态行程规划产品计划书

> **文档版本：** 1.2　|　**更新日期：** 2026-09-27
> **用途：** 单城最小可用产品的功能范围与实现边界
> **当前状态：** 产品文档与 HTML 原型；尚未开始应用实现。

## 1. 产品目标

用户告诉路书“什么时候到、住在哪里、能玩多久、喜欢什么”，系统根据可追溯的地点数据、营业信息、天气和真实路线，生成按日期和时间排列的旅行计划。

首版服务第一次到访、没有时间逐篇整理攻略、已经确定酒店和交通的用户。先覆盖一个城市的一至数日旅行，验证计划是否顺路、时间是否合理、用户能否方便地调整。

重庆是现有原型的演示城市，正式试点城市待确认。初期地点数量以能人工核验为准；先准备覆盖白天、夜间、美食、雨天和返程场景的一小批地点。

## 2. 核心使用流程

1. 输入城市、日期、到达/离开时间、到达/返程地点和住宿位置。
2. 选择兴趣、节奏、交通方式、步行接受度、同行情况和饮食限制。
3. 系统从已核验地点中筛选候选，查询天气与交通耗时。
4. 规划器安排游玩、用餐、交通、休息和返程缓冲。
5. 用户在时间线与地图中查看每天的安排和地点详情。
6. 用户锁定已确定的活动、替换地点或采用雨天备选，系统重排受影响区段。
7. 保存计划，退出后可以重新打开。

当到达/返程地点影响交通缓冲但尚未提供时，应提示补充，不能声称已计算完整接驳。定位是可选输入方式，拒绝定位后仍可手动选择酒店和起终点。

## 3. 首版功能

| 能力 | 首版做到什么程度 |
| --- | --- |
| 出行信息 | 表单为主，日期时间与必填字段有校验 |
| 候选地点 | 单城、人工维护的有限数据集，包含景点、美食和室内备选 |
| 行程生成 | 考虑可用时间、营业、交通、用餐、天气和个人限制 |
| 地图 | 真实底图、地点序号、路线及按日切换 |
| 地点详情 | 推荐理由、营业信息、来源、更新时间和不确定状态 |
| 行程调整 | 锁定、替换、移除及局部重排；重新校验交通和时间 |
| 保存 | 保存结构化行程及采用的数据，重新打开后保持；重排失败保留原计划 |
| 发现与我的 | 少量人工主题内容、已保存行程和偏好，不建设内容社区 |
| 后台 | 地点维护、营业信息编辑、来源审核、生成行程查看、简单规划参数 |
| 大模型 | 主流程跑通后接入需求解析、用户提供文本的线索提取和推荐说明 |

大模型接入前，表单和固定规则说明应能完成核心流程。模型失败时保留已有结构化行程并使用规则说明。

## 4. 页面范围

移动端保留四个底部入口，地图作为行程页内的模式：

| 入口 | 内容 |
| --- | --- |
| 首页 | 创建计划、继续最近行程 |
| 行程 | 每日时间线、地图、天气提示；进入地点详情与调整页面 |
| 发现 | 少量人工维护的试点城市主题和体验 |
| 我的 | 保存的行程和出行偏好；收藏可后补 |

创建计划、生成状态、地点详情和调整行程作为子页面。切换日期时，时间线、地图标记和路线使用同一份当天数据；切换视图保留当前日期和选中地点。

后台页面按最小功能组织，不要求照搬原型的八个完整模块。路线方案与用户行程可以先合并为行程查看；推荐权重只做简单配置，不做版本发布和回滚平台。

现有两份 HTML 保留为视觉和交互参考。逐页范围见[原型说明](../prototypes/README.md)，原型中的全部按钮不构成首版必做清单。

## 5. 数据和事实来源

每个地点至少包含名称、城市、类别、坐标及坐标系、建议停留时间、适合时段、室内/室外属性、营业信息、来源和最后核验时间。

营业信息应能表达每周时间段、跨午夜营业、临时关闭和未知状态。来源保留链接或录入依据、摘要、发布时间（如有）、核验时间，以及待核验、已核验、冲突、过期状态。

- 首批数据可人工录入或通过固定样例导入，样例与真实数据明确区分。
- 来源链接先作为证据保存；用户提供的文本可后续交给模型提取线索，不承诺任意网页自动抓取。
- 核心事实冲突或缺失时，提示核验或排除候选，不生成声称可执行的确定安排。
- 交通距离、耗时和路线来自地图服务；天气来自天气服务。
- 远期天气不在预报范围时标记“天气待更新”，可提供室内备选但不预测具体天气。
- 内容使用人工整理、授权来源或用户主动提供的材料，不依赖未经许可的批量采集。

## 6. 规划规则

规划器用 TypeScript 编写，按“过滤 → 评分 → 排程 → 完整校验”执行。

硬约束包括可用时间、营业时间、交通时间、不可重叠、锁定活动、饮食限制和返程缓冲。兴趣、顺路程度、地点特色、天气适配和信息新鲜度用于排序，分数不能覆盖硬约束。

第一版使用简单的候选过滤、按区域分组、贪心插入和局部顺序调整。每项活动计入停留、交通和缓冲；无可行方案时减少活动或说明冲突，不硬塞地点。

“锁定”指用户确认的活动及时间不能被自动修改，属于产品功能。局部重排保留锁定和已完成活动，只处理受影响区段；无法满足时说明原因并保留原计划。

天气变化先由用户刷新或主动选择雨天备选触发，不做后台自动监测和推送。移动端生成状态展示真实进度或等待状态，不将固定动画当作真实处理进度。

## 7. 数据保存与访问

核心数据包括城市、地点、营业信息、来源证据、旅行需求、每日行程、行程项目、交通段、天气快照和推荐原因。偏好先随行程保存，之后按需要加入用户账户。

个人本地演示阶段可以使用单个演示账户或匿名会话，暂不支持跨设备同步。不应使用可猜测的设备编号作为访问私人行程的凭证。对外提供服务前，应增加用户/管理员认证及行程归属检查；不建设复杂角色体系。

行程保存生成时的数据和依据。打开旧行程不能静默替换为新结果；更新天气或重排由用户触发。服务端密钥不返回手机或浏览器。

## 8. 暂缓范围

- 多城市自动规划、预订支付、社交、分享共编和多个方案对比。
- 独立收藏系统、行为学习、自动个性化推荐和复杂预算优化。
- 任意攻略链接自动抓取、全平台采集、自动监测闭店与天气推送。
- 数据分析大屏、独立路线模板运营系统、多角色权限、完整审计报表和运维控制台。
- 推荐规则版本发布、回滚平台、模型训练、向量检索和 GPU 环境。
- 五人分工、并行任务书、CI/CD、提交门禁和成套自动化测试平台。

后续按真实需求增加，不作为单城主流程的前置任务。

## 9. 怎么判断首版可用

用真实地点与路线逐项走查即可，不要求先搭专用测试平台：

- 晚到当日没有到达前的安排，并留出入住交通时间。
- 完整日包含游玩、用餐、交通和休息，营业时间内可到达且完成活动。
- 返程日留足到车站或机场的接驳时间。
- 雨天有可用室内备选；没有备选时说明原因。
- 锁定一个活动后替换另一个，锁定活动仍保留。
- 时间线和地图在切换日期、替换地点后保持一致。
- 保存后重新打开仍能看到同一行程。
- 后台修改并核验地点后，新生成行程使用更新数据。
- 地图、天气或模型失败时有清晰提示，不产生虚构事实或覆盖原计划。
