## 4. Q-01：输入、日期与自然语言

### 推荐方案

参考携程按目的地、天数和风格组织规划的公开入口，以及美团按具体场景理解偏好的思路，采用“基础信息 → 偏好 → 确认”的三步输入。[携程说明](https://www.ctrip.com/tripplanner)、[美团说明](https://www.meituan.com/news/NN260727198008607)

| 字段组 | 首版要求 / 推荐默认 |
| --- | --- |
| 城市与日期 | 城市固定重庆；连续 1～3 日，开始日不得晚于结束日；超范围提示拆分需求，不默默截断 |
| 每日窗口 | 普通完整日预填 09:00–20:00，明确可编辑；首日/末日以确认的到离条件裁剪；晚到不能套用早上出发 |
| 起终点 | 每日必须能确定起点与终点；有住宿时默认展示为住宿点，用户可改；住宿未定可选明确地点；同名地点必须选择具体 POI |
| 到达方式 | 选择“已在市内”或“从交通枢纽到达”；后一种必须填枢纽与到达时间，交通与入住另计 |
| 返程 | 选择“当天继续住宿”或“需要赶车/机”；后一种必须填出发时刻、准确终点与已确认缓冲 |
| 交通 | 默认允许公共交通和步行；打车需用户主动允许；不由模型自动扩大可用交通方式 |
| 节奏 | 默认均衡；轻松/均衡/紧凑作为软偏好，不能覆盖硬约束 |
| 饮食、步行限制 | 未填写表示未设置该约束；用户主动声明的禁忌/上限需回显，不自动替用户解除 |
| 兴趣、预算、同行 | 可选；预算按每人每日人民币表达且注明仅作偏好；缺价格时不承诺预算满足；不从人数推断年龄/健康信息 |

- 时间输入和页面展示统一 `Asia/Shanghai`；接口使用带偏移的 ISO 8601 时刻并保留时区，数据库由 D 统一按 UTC 保存时刻；纯日期字段不误作 UTC 零点。
- 首版自然语言仅支持文本，建议上限 500 字；用于提取已有表单字段及“换一站、少走路、改为室内”三类修改意图。语音、图片攻略识别和订单邮箱读取暂缓。
- 提取结果必须回显供用户确认。关键问题一次集中询问，建议最多 3 项；未答关键时间/位置则保留草稿，不能自行猜补成可行计划。
- 普通推荐每天先尝试 2～4 个非餐饮活动及必要用餐；晚到与返程自动减少活动数量。这是软目标，时间/营业/路线优先。

### 验收与责任

- 增补“住宿未定但手动起终点有效”“跨日到达”“自然语言时间有歧义”“同名地点未选择”的输入样例。
- US-02 / AC-02：确认前字段不可被直接当作有效规划约束；表单与自然语言最终使用同一结构。
- A 组织会签；B 表单；D 时间/地点字段；E 抽取与追问。第 1 周确定产品行为，TB-0106 冻结字段。

## 5. Q-02：锁定与局部重排

### 推荐方案

Wanderlog 的按日路线组织可作为交互参考；锁定规则是 Trailbook 自身推荐，不推断竞品的预约约束算法。[Wanderlog FAQ](https://wanderlog.com/blog/faq/)

1. 首版“锁定”同时固定地点 ID、所属日期、开始与结束时间。已完成活动及其之前已执行区段只读。
2. 支持替换一站、移除未锁定站点、采用雨天备选、改变当日节奏；默认只影响当前日期。首版不自动跨天搬移活动。
3. 两个锁定节点之间作为一个可调整区段；修改后重算相关交通、缓冲与当天约束。不能为了保留未锁定活动而改变固定预约。
4. 展示“移除/新增/时间变化/步行变化/原因”的预览，用户确认后保存新版本；未确认时原计划仍有效。
5. 冲突时提示涉及的约束及可选动作，例如解除某项锁定、放宽时间或不采用替换；不自动替用户选择。
6. 保存附带原版本号；若原版本已变化，返回版本冲突并重新加载，不能覆盖他人/另一请求已保存的结果。

### 验收与责任

- 使用 SC-CQ-03、AT-06 检查锁定字段逐项一致、失败保留原版本、取消预览不保存、旧版本写入被拒绝。
- E 定义区段与冲突，D 实现版本/原子保存，B 实现预览，A 确认行为；TB-0106 完成定义。

## 6. Q-03：少走路、步行总量与未知

### 推荐方案

| 输入 | 建议行为 |
| --- | --- |
| 均衡/未设步行限制 | 优先减少无效折返；不伪造一个用户未选择的硬上限 |
| 选择“少走路” | 显示可编辑目标：每日 3000 米、每个交通段步行 800 米；默认是软目标，超目标给出说明 |
| 勾选“不得超过”并确认数值 | 对对应数值执行硬过滤；不能达成时说明冲突，不能悄悄降级为软偏好 |
| 已填写自定义值 | 自定义值优先；六类样例中的 2000/500 米仍按样例原值执行 |

- 总步行 = 所有交通段的步行/接驳距离 + 所选地点的场内步行。交通“总耗时”已含接驳时，不重复增加接驳时间。
- 单段上限针对每个 RouteLeg 的步行部分；场内步行单列并计入全日总量。距离内部以米保存，显示四舍五入不参与边界判断。
- 场内未知时显示“总量未包含该地点场内步行，无法完整核验”。硬上限模式下，这个候选不能成为“已满足上限”的结果；软偏好可展示带说明的备选。
- 不把路线距离直接换算成可靠台阶/坡度或健康适宜结论。重庆坡道、扶梯、立体通道等属性由 D 验证服务数据、C 补充地点核验。
- 3000/800 米为降低首版交互复杂度的起始推荐，并非体力标准；试点后按用户替换和反馈调整。

### 验收与责任

- SC-CQ-05 继续验证 1800 米精确求和、接驳不遗漏、未知不填零。
- 增补软目标超出可显示风险、硬上限超出不能成功、用户自定义覆盖默认三项。
- D 路线/单位，C 场内数据，E 约束，B 输入/提示，A 会签；TB-0102/0106 完成。

## 7. Q-04：缓冲和返程截止

### 推荐方案

以下为表单与规则的推荐起始值，均向用户显示并允许修改；不表示铁路、航空或场馆的服务规定。

| 项目 | 推荐起始值 | 约束 |
| --- | --- | --- |
| 到活动地点后的转换 | 10 分钟 | 活动开始前预留；路线服务已包括的接驳不重复计时 |
| 首日办理入住 | 30 分钟 | 用户选择不入住/已入住可为 0；不能因晚到而自动删掉 |
| 返程取行李 | 20 分钟 | 用户声明需要时，必须包含回住宿点的路线与停留 |
| 火车最晚到站缓冲 | 60 分钟，须确认 | 班次发车时间减缓冲得到截止；遇更长的实际要求由用户覆盖 |
| 国内航班最晚到机场缓冲 | 120 分钟，须确认 | 需明确机场/航站楼；实际航空/机场安排优先；产品不保证一定赶得上 |
| 国际/其他特殊返程 | 不自动提供时长 | 首版要求用户自行填写确认后的最晚到达时刻 |

用户填入班次时间但未确认缓冲时，计划保持待补输入。只有用户设置或确认后的数值才成为硬约束；六场景的 90 分钟缓冲继续作为自定义测试值。

`最晚到达终点 = 班次时刻 - 已确认缓冲`。末站到终点的交通、回酒店绕行和取行李都必须参与计算；终点到达恰等于截止视为满足，晚一分钟视为冲突。固定停留不能被自动缩短。

### 验收与责任

- 沿用 SC-CQ-01/02/04，并增加默认缓冲未确认、改为更大自定义缓冲、取行李绕行不能省略的检查。
- A/E 规则，B 确认交互，D 字段与时间运算；TB-0101/0106 完成。

## 8. Q-05：状态、恢复与性能

### 推荐状态和保护规则

- 行程记录区分 `draft`（草稿）与 `ready`（已校验可用）。有未满足硬约束的结果可以作为草稿展示，不能标成完整成功。
- 规划任务候选状态：`queued`、`running`、`needs_input`、`succeeded`、`failed`、`cancelled`。英文取值待 D/E 在共享契约正式发布，用户界面使用清晰中文。
- 原因至少区分输入缺失、没有候选、约束冲突、路线未知、供应商超时/配额、模型格式错误、版本冲突。天气未知可为警告，不无条件使整个计划失败。
- 同一操作带幂等标识；相同用户、标识和内容重复提交返回原任务/结果，建议保留 24 小时；同标识不同内容拒绝。用户修改条件后创建新操作。
- 成功保存采用版本校验和事务；失败保留输入与原行程；模型解释失败可用规则化说明，关键事实不可由模型补造。

### 推荐性能与重试预算

| 项目 | 推荐目标 / 上限 |
| --- | --- |
| 普通查询与维护请求 | P95 ≤ 2 秒；按约定试点环境记录客户端与服务端耗时 |
| 规划任务 | P95 ≤ 30 秒；从服务端接受任务到完成/终止总截止 60 秒，含排队与重试 |
| 地图 / 天气单次请求 | 分别 10 秒 / 5 秒超时，均受剩余总时限限制 |
| 模型单次请求 | 20 秒上限；输入解析和解释按需调用；整项规划最多 3 次模型调用，包含修复/重试 |
| 自动重试 | 每个逻辑外部请求最多 1 次，仅限可恢复的网络/限流/临时服务错误；在总预算不足时不重试；遵守供应商重试提示 |
| 模型输出修复 | 最多 1 次，计入上述调用与总时间；仍不合格则失败或使用可验证的规则结果 |
| 进度 | 显示阶段与耗时，不伪造完成百分比；超时后提供可恢复入口 |

以上数字是工程目标，不是承诺已有性能。初次测量建议固定数据、同一提交、并发 5，至少 50 次普通请求与 30 次规划任务；分别报告冷/热缓存、失败数、等待队列、第三方耗时和 P95。超时必须计入失败及耗时分布，不只统计成功快请求。

### 验收与责任

## 9. Q-06：一个月留存与到期清理

### 推荐计时规则

1. `expiresAt = firstStoredAt 加 1 个日历月`，按 Asia/Shanghai 计算月底日期，再保存为 UTC 时刻。不是固定 30 天，也不是统一到当月月底。
2. 原始内容首次成功保存起计时；原文发布时间另存，不作为本次留存起点。普通编辑、失败重试和重复导入不延长原记录期限。
3. 若目标月无对应日，取目标月最后一天、保持当地时分秒。例如模拟的 2026-01-31 10:00 到期于 2026-02-28 10:00；2026-09-26 10:00 到期于 2026-10-26 10:00。
4. 内容确有新版本并重新获取时建立新证据版本和真实采集时间；不能通过复制旧正文规避到期。

### 推荐清理范围与执行

| 数据 | 推荐处理 |
| --- | --- |
| 原文、上传文本、摘录、截图及可还原内容的解析摘要 | 共用原证据到期时间；首版尽量只保留必要片段与来源，不保存整页/整段视频 |
| 来源 URL、引用缓存、用户端证据缓存 | 证据到期后停止提供原始内容及来源详情；过期引用展示“来源证据已到期”；客户端在线刷新清理，离线也按到期时间禁止展示 |
| 清理时限 | 到期瞬间按时间判断为不可访问；清理任务每 15 分钟执行一次，首次物理清理目标为到期后 15 分钟内；失败记录并告警，不延长有效期 |
| 备份 | 原始证据内容与可还原副本不进入常规长周期备份；若对象存储有版本历史，也须受同一期限处理；恢复其他备份后先执行到期校验再开放读取 |
| 日志 | 普通日志不记录证据正文、完整输入、密钥或精确个人位置；建议保留 30 天脱敏技术日志 |
| 最小审计记录 | 仅保留内部 ID、来源平台、处理动作、操作者内部 ID、时间、清理结果，建议 90 天；不保留正文、URL 或可还原摘录 |
| 已核验地点事实 | 独立记录核验依据与有效期；唯一支撑证据到期时转待复核/过期，不自动维持“已核验”；独立有效核验仍可按规则使用 |

15 分钟是清理任务的执行目标，不增加证据可访问时长。若供应商、存储或备份机制不能满足选定的留存范围，应调整存储方案后再接入原始证据。

模型调用优先发送已核验的结构化事实。需要发送来源文本时，先由 A/D 确认供应商的数据处理设置符合本项目规则；无法确认时首版采用人工整理，不把原文发送给该供应商。本节是项目数据处理方案，不能据此认定取得了某个平台的内容使用授权。

### 验收与责任

AT-13 增加月底/非月底、到期前后 1 秒、重复导入、缓存到期、任务失败重试、备份恢复检查。A/C 定规则，D 实现生命周期；TB-0105 会签。

## 10. Q-07：来源、事实核验与餐饮

### 推荐状态与准入

| 对象 | 候选状态 | 准入规则 |
| --- | --- | --- |
| 来源处理 | 待审核 / 通过 / 退回 / 忽略 | 导入或抽取成功只到待审核；通过才可作为来源依据 |

## 11. Q-08：统计口径与反馈

### 推荐指标定义

所有报表展示 Asia/Shanghai 日期范围、数据截止时刻、城市、规则版本和 Mock/真实标记。试点默认排除 Mock；重复传输按 `eventId` 去重，同一幂等操作的重试不计新请求。

| 指标 | 推荐定义 |
| --- | --- |
| 规划请求数 | 时间窗口内首次被接受的独立规划操作数量；表单本地校验失败不计入 |
| 完整规划成功率 | 同一请求时间队列中 `succeeded / (succeeded + failed)`；排队/运行/待补输入/取消分别列数，不藏入成功；报告数据截止时间 |
| 有效计划保存率 | 该窗口内首次生成成功的不同 Trip 中，截止报表时至少成功保存一次的 Trip 数 / 该队列生成成功 Trip 数；同一 Trip 多版本不重复计 |
| 当期保存量 | 保存事件发生在窗口内的不同 Trip 数；与上项队列指标分别命名，允许包含更早创建的行程 |
| 替换成功率 | 成功提交新版本的独立替换操作 / 已终结的替换操作；生成了预览但未确认不算成功保存 |
| 错误率 | 各类失败规划操作 / 已终结规划操作；同时展示错误类别、供应商和规则版本 |
| 反馈量 | 独立反馈 ID 数；分类为地点错误、营业错误、路线不合理、饮食冲突、体验建议；处理状态可追踪 |

分母为 0 时显示“暂无可计算数据”，不显示 0% 或 100%。总览与分析使用同一统计口径，不允许在两个页面各自计算。

AT-12 的 3 次请求（2 成功、1 失败），若两个成功结果对应不同 Trip 且其中 1 个保存，则规划成功率为 2/3、有效计划保存率为 1/2；同一事件再传输一次，数值不变。超窗口与 Mock 事件按筛选规则处理。

### 责任

A 定口径与复算例子，C 页面，D 事件/查询；阶段 1 定稿，TB-0201 前确定字段。统计用例不需要先实现复杂数据仓库。

## 13. Q-10：真实数据与外部服务

### Q-10a 地图与路线

推荐高德作为首个地图/路线 Provider，百度用于人工交叉核验，不做两套 SDK 自动切换。高德官方提供多交通方式路线 API 和坐标转换说明。[路线 API](https://lbs.amap.com/api/webservice/guide/api/newroute)、[坐标说明](https://lbs.amap.com/api/javascript-api-v2/guide/transform/convertfrom)

- Trailbook 的高德适配路径统一使用带坐标系标记的 GCJ-02 经纬度，明确 `longitude/latitude` 顺序；保留输入坐标系与来源，非高德数据只在受控边界转换，避免重复转换。
- 默认路线覆盖公共交通、步行；用户允许时加入驾车/打车参考路线。所选路线必须能取得耗时和接驳步行；缺字段依 Q-03 降级。
- D/B 用真实 Android 设备或模拟器验证实际 React Native/Expo 集成，不用网页地图截图代替移动 SDK 成功证据。

- 权限、真实点线、坐标位置、网络失败、配额和授权/缓存条件均须记录；失败时保留可用时间线，不能画虚构线路。

### Q-10b 天气

推荐和风天气作为首个候选，原因是官方分别提供逐日和逐小时预报文档，适合验证天气快照输入。[逐日 API](https://dev.qweather.com/docs/api/weather/weather-daily-forecast/)、[逐小时 API](https://dev.qweather.com/docs/api/weather/weather-hourly-forecast/)

- 推荐产品口径：未来 72 小时内若账户有相应小时数据，则用于活动时段；未来 7 日内用实际可取得的逐日预报；更远日期显示“天气待更新”并给条件式室内备选。接口返回范围更短时，以实际范围为准。
- 适配器记录预报适用时间、供应商发布/更新时间（有则保留）、本次获取时间与来源；不能把获取时间冒充发布时刻。
- 推荐降雨提示：对应时段概率达到 60% 或天气类别为降雨时提示室内备选；强降雨/雷暴等类别触发受影响户外项目复核。概率未知不按 0；日数据不能捏造成小时雨段。
- 缓存刷新建议 60 分钟，前提是服务条件允许；过期或超时显示时间与未知状态。用户确认后再替换，不新增自动后台推送。
- D 负责 POC，E 确认类别/单位与规划规则；供应商真实覆盖、字段、调用条件待实测。

### Q-10c 模型与结构化质量

推荐百炼 `qwen3.7-plus-2026-05-26` 作为首个 POC 候选，采用 JSON Schema 输出并由本地契约/业务规则再次校验。官方模型页给出对应快照，结构化文档列出该系列支持情况。[模型页](https://help.aliyun.com/zh/model-studio/qwen3-7-plus)、[结构化说明](https://help.aliyun.com/zh/model-studio/qwen-structured-output)

- 使用团队选定地域的 API，先确认账户能调用指定快照；不可用时由 E 记录替代候选和重新测量，不静默换模型或地域。
- 首版仅调用文本解析/说明能力；不启用自主订票、GUI 操作、联网补事实等能力。时间可行性由规划规则计算，地图/天气/营业来自对应数据。
- 采用固定模型/提示词/规则版本；已验证排程即使解释模型失败，也可返回规则化说明。
- 推荐评测集：六类场景各 10 个输入（4 正常、3 边界、3 缺失/冲突），共 60 个；每个运行 3 次，共 180 次评测。沿用现有 18 主变体并补充，不声称当前已执行。
- 推荐门槛：首轮 Schema 合格至少 171/180（95%）；最多一次修复后至少 179/180；关键约束抽取语义正确至少 171/180，未达标项必须列出类型。无返回/超时按该轮未通过计，不删掉失败样本。
- 硬约束检查要求：所有最终标为成功的结果均不能违反锁定、时间、忌口和显式步行上限；模型错误须被拦截。另统计已知可行正常样例的实际生成率，避免靠全部拒绝达到“零违规”。
- 规划层对 18 个主变体应全部给出预期行为；正常可行输入必须产出可行方案，预期失败输入按指定原因处理。上述门槛由 A/E 会签，功能实现后执行。

- 调用前预留本次费用上限，结束后按实际用量回填，避免并发任务重复使用剩余预算；供应商账单用于复核。无法给出可靠单次费用上界的付费能力先不启用，由 D/E 补充费用控制方案。
- A 负责预算与账号归属登记；D 管地图/天气及服务端配置；E 管模型参数；C/B 只使用必要的受限权限。每个账号指定一名实际保管人和一名备份联系人，团队填写姓名，文档只记角色不记密钥。
- 首版单用户建议每分钟最多 3 次创建/重排、全服务同时最多 5 个规划任务；其余排队受 60 秒总截止约束。D 按配额和 POC 数据调整后记录版本。

Q-10 各项推荐已给出，实际账号可用性、商业条款、供应商数据和性能只能由 POC 证明，最晚第 2 周形成选型结论。
