# Trailbook 最小实现方案

> 更新日期：2026-09-27。本文按做出单城产品所需的依赖安排开发。当前先完成第二步中的移动端最小入口和首页 Web 预览；其他能力仍待实现。供应商与试点城市的确认尚未完成，不影响先做演示界面。

## 1. 技术结构

```text
手机 App：React Native + Expo ──┐
                               ├─ HTTPS/JSON → API：Node.js + Hono + Zod
后台网页：React + Vite ─────────┘                       │
                                        ┌──────────────┼──────────────┐
                                        ↓              ↓              ↓
                                  Prisma → MySQL    规划器          服务调用
                                                   TypeScript     地图/天气/大模型
```

客户端通过 API 访问数据；后端负责组织数据库、外部查询和规划流程。地图 SDK 在手机端显示地图，地图 Web API 在服务端提供路线计算。普通本地调试可以使用 HTTP，对外提供服务使用 HTTPS。

| 技术 | 它是什么 | 在项目里做什么 |
| --- | --- | --- |
| TypeScript | 带类型检查的 JavaScript 语言 | 写界面、API 和规划算法；具体数据单位仍要明确定义 |
| React Native | 手机界面框架 | 显示 Android/iOS 页面 |
| Expo、Expo Router | 移动端开发工具和路由方案 | 开发调试、设备能力、页面跳转和应用构建 |
| React | 网页界面库 | 显示后台表格、表单和详情 |
| Vite | 网页开发与构建工具 | 启动后台开发服务、生成发布文件 |
| Node.js | JavaScript 运行环境 | 运行 API 和开发工具 |
| Hono | 后端 Web 框架 | 接收 HTTP 请求，调用业务函数并返回 JSON |
| Zod | 运行时数据校验库 | 检查字段格式及必要的业务限制 |
| MySQL | 关系型数据库 | 持久保存地点、来源和行程 |
| Prisma | 数据库访问和建模工具 | 用 TypeScript 读写 MySQL，管理表结构变化 |
| HTTP/HTTPS、JSON | 网络协议、数据格式 | 传递请求和结果 |
| 地图、天气、大模型 | 远程服务及 SDK | 提供路线事实、天气和语言处理 |

这些技术不是都属于 JS 框架，也不要求一次学完。按每一步需要的部分逐个使用即可。

## 2. 目录和模块边界

| 目录 | 后续职责 |
| --- | --- |
| `apps/mobile` | 手机页面、导航、地图显示、API 请求 |
| `apps/admin` | 后台页面、表单、API 请求 |
| `apps/api` | Hono 路由、输入校验、业务组合和基本访问控制 |
| `packages/contracts` | 共享数据格式、Zod Schema、错误结构 |
| `packages/database` | Prisma Schema、迁移、首批数据导入和读写 |
| `packages/planner` | 候选过滤、评分、排程、校验、局部重排 |
| `packages/providers` | 服务端地图、天气、大模型调用及统一结果格式 |

`apps/mobile` 已有 Expo 配置、首页路由和页面组件，其他应用及公共模块当前仅有 `.gitkeep`。详细文件在实现功能时创建，不预先铺开页面、仓储层或工具目录。

`apps/api` 组合四个公共模块；两个客户端可引用 `contracts`，不引用数据库和服务端 Provider。规划器接收地点、路线和天气数据，不直接联网或连接数据库，便于用固定输入验证。共享包不能依赖应用包。

地图等适配只放在 `packages/providers`，不再同时预建 `apps/api/src/providers`。不建设跨 Web/Native 的共享 UI 包、公共工具配置包、独立运维目录或预先分层的测试目录。

## 3. 顺序开发

下面是整体实现顺序，不是已完成清单。当前为学习与验证界面，先做移动端首页 Web 预览；正式接入地图和规划前仍需完成数据与服务边界确认。

### 第一步：确认数据和服务边界

选定一个城市与有限地点类别，准备覆盖晚到、完整日、雨天和返程的地点。选择一家地图、一家天气和一家大模型供应商。

在复杂手机页面开始前，做最小地图验证：底图、标点、路线绘制、坐标系、定位权限及目标设备能否工作。模型接入可以后置。

完成标志：知道地点从哪里来、地图如何显示与算路、天气覆盖到哪一天，供应商仍未知的部分有明确记录。

### 第二步：建立最小可运行入口

准备 Node.js 24 LTS，使用自带 npm。先在 `apps/mobile` 建立 `package.json` 和 TypeScript 配置，出现公共模块后再按需配置 npm workspaces，不一次性初始化所有目录。React Native 相关版本由所选 Expo SDK 的兼容要求决定。

先做手机端首页并用 Expo Web 预览；随后再建立后台启动页和 API 健康检查接口。基本忽略规则已配置，环境模板等实际需要密钥时再添加。当前在 `apps/mobile` 中执行 `npm run web`，不先建设根目录任务编排、代码检查平台、提交钩子或 CI。

完成标志：页面能打开，API 能返回 JSON，公共模块能被正确引用。当前只完成移动端首页 Web 预览及提示交互；后台、API、公共模块和原生端验证尚未开始，因此第二步尚未全部完成。

### 第三步：定义数据并连接数据库

先定义创建计划输入、地点、营业信息、每日行程、交通段和错误结构，再用 Prisma 建立 MySQL 表和首批数据。

时间统一明确日期与时区，停留和交通用分钟、距离用米，坐标附带坐标系；坐标顺序固定为经度/纬度。TypeScript 的 `number` 本身无法识别分钟和秒，不代替这些约定。

核心记录：City、Place、OpeningInfo、ContentEvidence、Trip、ItineraryDay、ItineraryItem、RouteLeg、WeatherSnapshot；偏好和推荐理由可先作为关联数据或结构化字段保存，不必拆成很多表。

完成标志：API 能读出真实存储的地点，能保存并重新读取一份行程。

### 第四步：用固定响应接通手机主流程

先让创建计划表单调用 API，返回明确标注的固定演示行程。做时间线、日期切换、地点详情和保存。随后让地图与时间线读取同一份每日行程。

后台先能查看和编辑地点及营业信息。UI 组件用基本 React/CSS 即可，shadcn/ui 等组件库按实际需要选用。

完成标志：输入 → 请求 → 结果展示 → 保存 → 重新打开可以连续操作。演示响应不代表规划算法完成，也不能用来通过真实路线验证。

### 第五步：接入真实地图和天气

地图 Provider 提供酒店地址检索、地理编码、地点间路线及交通耗时。只开放已验证支持的交通方式；供应商没有矩阵接口时，对有限候选按配额逐对查询。

天气 Provider 返回预测日期、查询时间和可用预报；超出范围返回未知。调用必须设置超时，对服务失败返回清晰原因，不自动用假路线替代。

完成标志：候选地点有真实交通数据，地图画出对应路线，天气信息可追溯；请求失败有可恢复提示。

### 第六步：实现确定性的规划器

1. 过滤城市不符、核心信息不可靠及不满足个人限制的候选。
2. 根据兴趣、时段、天气、信息新鲜度和顺路程度评分。
3. 固定酒店、到达/返程地点和锁定活动等锚点。
4. 按区域分组，在用餐和游玩时间窗中插入地点。
5. 计入交通、停留和缓冲，尝试局部交换以减少绕路。
6. 完整检查活动是否重叠、是否在营业时间内、是否留足返程时间。
7. 无解时减少活动或返回不可行原因，不输出违反硬约束的“成功”结果。

完成标志：固定输入得到可解释的结构化行程，晚到、雨天、返程等场景符合规则。

### 第七步：实现锁定和局部重排

用户锁定活动后，替换其他地点应保留锁定的地点和时间。替换/删除会影响相邻交通段，必须重新查询或使用有效路线数据并校验时间。

只重排受影响区段，保留已完成活动；冲突时保留旧行程并说明原因。保存行程和项目等关联数据时使用数据库事务，避免留下半份结果。

完成标志：锁定晚餐后替换下午活动，晚餐不变；不可行替换不会覆盖原计划。

### 第八步：补齐简单后台

在地点编辑基础上增加来源录入、核验状态、来源与地点关联、生成行程查看以及推荐参数编辑。未核验或核心事实冲突的记录不直接发布为正式候选。

权重和必要时间范围能编辑即可，不做规则版本平台、统计大屏、任务队列或完整服务配置控制台。后台不显示服务端密钥。

完成标志：人工维护的真实地点能进入下一次规划，过期或错误地点能被修正或停用。

### 第九步：接入模型辅助

模型将自然语言解析为偏好，将用户提供的文本解析为待核验线索，并为规划器的既定结果组织说明。输出必须经过 Zod 检查和事实关联检查。

模型不修改已经确定的路线、营业时间和排程事实；失败时使用表单输入和规则说明。结构校验通过不等于事实正确。

完成标志：使用自然语言也能进入相同规划流程，模型不可用时表单主流程仍能工作。

### 第十步：真实走查和发布

按照[产品计划中的走查清单](../product/product-plan.md)验证完整流程，再部署 Node.js API、MySQL 和后台静态文件，构建手机应用。Windows 可先验证 Android，iOS 按实际构建条件安排。

本地个人演示可以暂缓登录。对外使用前补基本用户/管理员认证、行程归属检查和 HTTPS；私人行程与管理写接口不能公开访问。不建设复杂的多角色权限平台。

完成标志：目标手机可以访问已部署服务，保存数据重启后仍在，晚到、返程、雨天和服务失败行为得到确认。

## 4. API 草案

具体字段在实现时确定，以下仅表示核心功能范围：

| 操作 | 接口草案 |
| --- | --- |
| 创建与查看旅行 | `POST /trips`、`GET /trips/:id` |
| 生成和查看行程 | `POST /trips/:id/generate`、`GET /trips/:id/itinerary` |
| 局部重排 | `POST /trips/:id/replan` |
| 锁定/解锁 | `PATCH /trips/:id/items/:itemId` |
| 查询地点 | `GET /places`、`GET /places/:id` |
| 地点与营业信息维护 | `GET/POST /admin/places`、`PATCH /admin/places/:id` |
| 来源录入与审核 | `GET/POST /admin/evidence`、`PATCH /admin/evidence/:id` |
| 查看行程和配置参数 | `GET /admin/trips`、`GET/PUT /admin/rules` |

Zod 除了字段类型，还要检查日期格式、结束时间晚于开始时间、有效范围及权重等规则。只写 `z.string()` 不代表日期合法。

## 5. 哪些配置留到有需要时

- 暂不要求 ESLint、Prettier、Vitest、Playwright、Husky 或 GitHub Actions；仍要实际验证功能和规划约束。
- npm 正常产生的 `package-lock.json`、Prisma 数据库迁移是开发产物，应正常保留。
- Docker Compose、接口调试工具、组件库和客户端缓存库均可选。
- 不引入 Redis、队列、微服务、Kubernetes、向量数据库和自训练模型。
- 不规定五人分工、周报、并行任务编号和跨设备验收报告。

环境准备见[最小开发环境](development-environment-setup.md)，原型对应关系见[原型范围说明](../prototypes/README.md)。
