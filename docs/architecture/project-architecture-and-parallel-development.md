[https://github.com/luoyjlyj/Trailbook.git](https://github.com/luoyjlyj/Trailbook.git)

## 文档说明

本文档根据以下三份材料整理：

- 产品计划书：作为产品目标、MVP 范围、技术方案和团队职责的主要依据。
- 移动端交互原型：作为移动端页面、用户流程和交互状态的依据。
- Web 管理后台原型：作为运营端模块、内容审核和规则配置流程的依据。

原型中的按钮、地点、天气、路线、评分和数据均属于演示内容，不应直接视为已实现功能或真实业务数据。

# 二、并行开发阶段

| 阶段 | 参考周期 | 阶段目标 |
|---|---:|---|
| 阶段 0：项目初始化 | 2–3 天 | 建立仓库、规范和开发环境 |

# 五、MVP 完成标准

- 用户可以填写城市、日期、住宿起点、兴趣、节奏和必要限制。
- 系统可以生成按日期和时间排序的行程。
- 行程包含景点、美食、停留时间、交通段和弹性时间。
- 地图和时间线展示同一份行程数据。
- 支持地点详情、推荐理由、来源和更新时间。
- 支持替换地点、雨天备选和局部重排。
- 已锁定地点在重排后仍然保留。
- 后台可以审核来源、维护地点、配置规则和查看反馈。
- 外部服务失败时有清晰提示。
- 系统不会把演示数据、模型猜测或过期信息伪装成真实事实。

# 六、GitHub 协作规范

- `main` 只保留可演示或可发布版本。
- 使用 `feature/mobile-*`、`feature/admin-*`、`feature/api-*`、`feature/planner-*` 分支。
- 所有功能通过 Pull Request 合并。
- 每个 PR 说明变更内容、测试方式和影响范围。
- 共享接口变更需要 B、C、D、E 共同评审。
- 数据库 Schema 变更必须附带迁移文件。
- 不提交真实 API Key、用户数据和未经授权的内容。
- 合并前通过类型检查、Lint、相关测试和代码审查。
- Mock 数据必须显式标识为演示数据，不能当作线上事实。

# 九、任务完成定义（Definition of Done）

一个开发任务只有同时满足以下条件才可以关闭：

1. 功能实现符合任务范围和共享契约。
2. 代码通过类型检查、lint 和相关测试。
3. 新逻辑至少包含正常路径和一个异常路径测试。
4. 接口或数据结构变更已更新文档和示例。
5. 不包含真实密钥、个人路径或未经授权的数据。
6. 加载、空数据、失败和重试状态得到处理。
7. 已由非提交者完成代码审查。
8. 已在集成环境或目标设备验证。
9. PR 中附有测试证据和影响范围说明。
10. A 按验收条件确认结果，但技术正确性仍由模块负责人和评审人负责。

# 十、风险与阻塞处理

| 风险 | 预警信号 | 处理策略 | 责任人 |
|---|---|---|---|
| 地图 SDK 与 Expo 不兼容 | 无法构建或路线能力缺失 | 第 1 周完成 POC；必要时使用 Development Build 或调整 SDK | B、D |
| 内容授权不明确 | 无法确认抓取和保留权限 | MVP 使用人工、授权和用户主动导入，不依赖批量抓取 | A、C |
| 地点数据质量不足 | 坐标、营业和名称冲突频繁 | 限制试点范围；增加核验状态和抽查门禁 | A、C、D |
| 模型产生事实错误 | 输出不存在地点或错误营业信息 | 事实字段仅来自数据库/服务；Schema 校验和证据引用 | D、E |
| 规划结果不可执行 | 时间重叠、跨区折返、无返程缓冲 | 硬约束先于评分；固定场景回归；不可行时减少地点 | A、E |
