## 1. 使用边界

本文件为后续人工验收、Mock API 和规划评测提供固定输入与判定依据，当前没有运行实现或访问真实供应商。

**城市背景为重庆；以下地点标识、营业时段、餐饮属性、步行量、路线耗时和天气全部是人为构造的测试数据。它们不是实地攻略、地图查询结果或天气预报。** 酒店只采用“解放碑区域住宿”的场景背景，不对应具体酒店。

- 所有日期使用 `Asia/Shanghai`（UTC+08:00），测试周末为 2026-10-16 至 2026-10-18。该日期仅用于固定输入，不隐含届时天气或地点营业情况。
- 时间区间按 `[开始, 结束)` 理解；活动结束等于营业截止时刻、到达终点等于最晚到达时刻，可判定满足。时间精度和存储格式待数据字典冻结。
- 时间、步行和缓冲数值只用于本组样例，不是全体用户的产品默认值，也不代表出行建议。
- 正常用例的示例排程是一种可行答案。除锁定/边界用例明确固定的条件外，可接受其他满足全部约束、且使用允许数据的排程，不以文字完全一致作为通过条件。
- 失败变体若按预期返回可恢复提示、保留原数据，属于该验收用例通过；“业务未生成计划”不等于“测试失败”。
- 以下标识与中文状态均为验收术语，不提前确定 DTO、数据库字段或最终错误码。

### 2.3 其他共同参数

- 到活动地点后，活动开始前至少保留 **10 分钟**转换缓冲；酒店/车站等终点无需额外套用这项活动缓冲。
- 地点固定停留时长不能被算法自行缩短；需缩短时应由用户重新确认。
- 完整日正常天气设为“晴，Mock”；雨天用例设为“12:00–18:00 大雨，Mock”。模拟快照查询时间为对应日期 08:00，记录来源 `CQ-MOCK-weather`。
- 默认交通允许乘车和步行，正常日节奏均衡；没有明确步行数值时，不凭空添加硬上限。
- 每条模拟地点/路线事实标注来源 `CQ-MOCK-0.1` 和对应数据更新时间；这些标记只用于识别测试数据。
- 示例结果须包括：日期、起终点、活动及地点 ID、开始/结束、停留时长、路线段及其方式/耗时/步行、转换缓冲、锁定状态、天气来源/更新时间、约束检查与冲突原因；精确字段由 TB-0106 决定。

| 字段 | 样例值 |

| 到达地点 / 时间 | A，19:30 |

### SC-CQ-01-N：正常路径

1. 输入上述条件并提交生成。
2. 查看当晚交通、入住、夜景和返回酒店的时间。
3. 切换地图/时间线，核对 N1 与 H 的顺序和同一行程版本；真实地图绘制另用 AT-04 验证。

一种可行结果：

| 项目 | 时间 |
| --- | --- |
| A → H | 19:30–20:15 |
| 入住 | 20:15–20:45 |
| H → N1 | 20:45–21:00 |
| 转换缓冲 | 21:00–21:10 |
| N1 夜景 | 21:10–21:50 |
| N1 → H | 21:50–22:05 |

通过条件：N1 开始不早于实际到达及转换完成时间；40 分钟停留全部在营业窗口内；22:30 前回到 H；没有同时追加全天景点或不必要晚餐。

### SC-CQ-01-B：营业截止边界

- 将到达 A 改为 **19:40**：最早可在 21:20 开始 N1，22:00 结束，22:15 回 H；应允许这个刚好结束于闭店时刻的结果。
- 将到达 A 改为 **19:41**：最早活动结束为 22:01，N1 不可排入。应解释剩余时间不足并安排休息/不排夜间活动，保留后续日期；不得缩短固定停留或忽略入住。

### SC-CQ-01-F：到店路线缺失

移除 A → H 的耗时。再次生成时应说明无法确认酒店可出发时间，保留用户输入并允许补充已确认的到店时间；不能把缺失交通当成 0 分钟后宣告计划可行。

证据：到达/入住/活动时间链、过滤 N1 的原因、原始输入与结果状态。

### SC-CQ-02-B：缩短可用时间

在 C1 09:30–11:00、L1 11:30–12:30 两项锁定条件下，将终点仍设为 H：

- 当天结束改为 **12:40**：午餐后 L1 → H 10 分钟，刚好满足；删除未锁定的下午活动。

### SC-CQ-02-F：事实未知

证据：完整时间预算、营业窗口核对、行程 ID/版本、未知字段处理结果。

## 6. SC-CQ-03：雨天

### 输入与前置条件

- 日期：2026-10-17；当天窗口 09:00–17:00，起终点 H。
- 原计划 V1：C1 09:30–11:00、L1 11:30–12:30、O1 13:00–14:00，之后 O1 → H 25 分钟；各段采用公共路线和缓冲。
- C1、L1 的地点、日期、开始与结束时间已锁定。原计划只含一个户外项目 O1，避免重复插入原有室内项目。
- 08:00 模拟天气快照更新为“12:00–18:00 大雨”；I1 为唯一可选室内替代，完整停留 90 分钟。

### SC-CQ-03-N：正常路径

1. 打开 V1，查看天气更新时间和 O1 受影响提示。
2. 请求雨天备选，检查变更预览，再确认采用。
3. 重新打开计划，比较 V1 与新版本。

一种可行调整：保留 C1、L1；12:30–12:50 从 L1 到 I1，12:50–13:00 缓冲，13:00–14:30 游览 I1，14:30–14:55 返回 H。

通过条件：锁定的四类字段不变；O1 被移除，I1 不重复；路线、时间线、地图数据同步新版本；变更摘要明确“因雨替换 O1”；新结果仍校验营业与路线，不能仅改文案。

### SC-CQ-03-B：备选闭店边界

- 将 I1 营业结束改为 **14:30**：最早 13:00–14:30 可完整游览，应接受。
- 改为 **14:29**：锁定午餐后无法完成 90 分钟停留；应说明没有满足条件的室内替代，不自动缩短停留或移动锁定午餐。原 V1 保留并标记雨天风险，用户可主动移除 O1 或修改条件后再规划。

### SC-CQ-03-F：天气不可用

清空天气快照并让天气服务超时：显示天气待更新/未知；可以给出条件式室内备选，但不能声称当天确定有雨或无雨。未确认替换前，不改写原行程。

证据：天气模拟快照、两版本结构化差异、锁定字段对比、失败时原计划仍在的记录。

## 7. SC-CQ-04：返程日

### 输入与前置条件

| 字段 | 样例值 |
| --- | --- |
| 日期 | 2026-10-18 |
| 当天出发 | H，09:00 |
| 返程班次 | R，17:00 发车，模拟 |
| 候车缓冲 | 90 分钟，仅本用例参数 |
| 最晚到站 | 15:30，即 17:00 减 90 分钟 |
| 取行李 | 必须回 H，停留 20 分钟 |
| 候选 | C1、L1；正常天气晴，Mock |

### SC-CQ-04-N：正常路径

1. 输入返程时间、终点、缓冲和取行李要求。
2. 生成后检查“最后活动 → H 取行李 → R”的完整链路。
3. 核对页面展示的最晚到站时刻和结构化结果一致。

一种可行结果：上午 C1 09:30–11:00，L1 午餐 11:30–12:30；12:30–12:40 到 H；12:40–13:00 取行李；13:00–14:00 到 R，早于 15:30。上午路线及缓冲同 SC-CQ-02。

通过条件：包含酒店绕行与取行李 20 分钟；不把 17:00 当作最后景点结束时间；不会在到站截止后追加活动；未因“已有余量”而漏掉候车缓冲。

### SC-CQ-04-B：到站截止边界

将取行李安排锁定为 H **14:10–14:30**：

- H → R 为 60 分钟：14:30 出发，15:30 到达，刚好满足。
- 将取行李改为 **14:11–14:31**：最早 15:31 到站，应判定与返程要求冲突；不自行减少候车缓冲，不静默提前锁定项目。

### SC-CQ-04-F：返程路线缺失

移除 H → R 路线耗时。因为取行李要求仍然存在，不能直接改成 L1 → R 并跳过酒店。应明确无法验证到站时间，允许重试/补充已确认交通条件，不能承诺赶得上。

证据：最晚到站公式、取行李约束、完整交通链、迟一分钟时的冲突结果。

## 8. SC-CQ-05：少走路

### 输入与前置条件

| 字段 | 样例值 |
| --- | --- |
| 日期 / 时间 | 2026-10-17，09:00–17:00 |
| 起终点 | H → H |
| 交通 | 允许乘车及其必要接驳 |
| 明确上限 | 每日总步行不超过 2000 米；每个交通段的步行不超过 500 米 |
| 统计口径 | 所有交通段接驳步行 + 所选地点场内步行；不把乘车段当作零步行 |
| 候选 | C1、L1、I1、O1；文化、美食偏好 |

这是普通少步行需求，不等价于无障碍路线认证。重庆坡道、台阶、场内路线是否有可靠数据，需要阶段 1 实地/服务核验。

### SC-CQ-05-N：正常路径

1. 明确输入两个数值上限后生成计划。
2. 查看逐段与场内步行，不只看交通方式标签。
3. 对照下面一种可行结果复算总量，并检查所有选中段。

可行顺序：H → C1 → L1 → I1 → H；时间可采用 C1 09:30–11:00、L1 11:30–12:30、I1 13:00–14:30，14:55 回 H。

| 步行项目 | 数值 |
| --- | --- |
| H → C1 接驳 | 300 米 |
| C1 → L1 接驳 | 400 米 |
| L1 → I1 接驳 | 200 米 |
| I1 → H 接驳 | 300 米 |
| C1 场内 | 300 米 |
| L1 场内 | 100 米 |
| I1 场内 | 200 米 |
| 合计 | 1800 米 |

通过条件：1800 ≤ 2000；各交通段步行 ≤ 500；未选择 H → C1 的 1800 米全程步行方案；不把 O1 高评分用来抵消上限。

### SC-CQ-05-B：总量与单段边界

固定上述 C1、L1、I1 的地点与时段，并固定采用该组已知直达路线，以便只检查上限：

- 每日上限 **1800 米**、单段 500 米：刚好满足。
- 每日上限 **1799 米**、单段 500 米：不可宣称满足；说明差 1 米，不按显示四舍五入抹掉超限。
- 每日上限 2000 米，单段上限 **400 米**：刚好满足；改为 **399 米**，C1 → L1 应触发冲突。

### SC-CQ-05-F：步行数据未知

移除 I1 场内步行或 C1 → L1 接驳步行值，分别运行：总步行应标为不完整，不能用 0 填补并声称满足 2000 米；可改选全部步行数据已知的可行方案，否则要求补充/修改。锁定了缺数据地点时先提示未知，不能悄悄删除锁定项。

证据：步行分项、总和、路线方式、超限/未知原因及锁定保护。

## 9. SC-CQ-06：饮食限制

### 输入与前置条件

| 字段 | 样例值 |
| --- | --- |
| 日期 | 2026-10-17 |
| 饮食硬限制 | 不吃辣、不吃牛肉 |
| 午餐窗口 | 11:30–14:00，需在窗口内完成 60 分钟用餐 |
| 候选 | L1 已核验满足；L2 已知冲突；L3 菜单未知 |
| 正常前序 | C1 09:30–11:00；C1 → L1 为 15 分钟 |
| 核验来源 | 仅公共模拟数据，不是真实菜单结论 |

### SC-CQ-06-N：正常路径

1. 在创建计划中填入两个限制并生成。
2. 检查午餐候选过滤原因及最终地点详情。
3. 保存后重新进入，确认限制和对应选择仍然存在。

预期可行结果：11:00–11:15 到 L1，等待/缓冲后 11:30–12:30 用餐。L2 因饮食冲突排除；L3 因事实未核验不能作为“确认满足限制”的候选。L1 的模拟核验依据和时间可查。

通过条件：两个限制都被保留；不能以“当地特色”“人气高”覆盖忌口；不可仅凭名称判断配料；仍校验路线、停留和营业时段。

### SC-CQ-06-B：午餐营业截止

保持必须完成午餐的要求，并把午餐前置到达 L1 的时刻固定：

- **12:50 到达**，缓冲 10 分钟后 13:00–14:00 用餐：刚好满足营业及午餐窗口。
- **12:51 到达**：最早 13:01–14:01，无法完整满足；不能压缩 60 分钟停留，也不能用晚餐窗口冒充午餐已满足。

### SC-CQ-06-F：没有可核验的匹配餐饮

移除 L1，只保留 L2 和 L3：应说明“当前没有已核验且满足这两个限制的午餐候选”。可以返回带明确未满足项的草稿，或请求用户补充地点/主动修改限制；不能静默推荐 L2，不能把 L3 标为确定不含牛肉或不辣，不能把未安排午餐称为完整成功。

证据：结构化饮食限制、三个候选的过滤原因、来源/核验状态、无解时原输入保留。
