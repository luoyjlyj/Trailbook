# 路书 Trailbook

城市旅行智能攻略与动态行程规划产品。

路书帮助用户回答一个具体的问题：**“我什么时候到、住在哪里、能玩多久、喜欢什么，接下来应该怎么走？”**

产品将攻略中的地点线索、特色美食、营业信息、天气和地图路线整理起来，结合用户的真实出行条件，生成按时间排列、可以在地图上查看、也可以随时调整的每日旅行计划。

> 当前状态：产品方案与交互原型阶段。仓库目前包含产品计划书和移动端、Web 管理后台原型；真实地图、天气、内容数据和 AI 规划服务将在后续开发阶段接入。

## 产品定位

路书不是简单地把网络内容交给大模型生成旅游文案，而是将旅行信息结构化，再由规则约束、路线规划和大模型解释共同完成行程规划。

核心原则：

- **计划要能执行**：每个安排都有地点、时间、停留时长、交通段和必要的缓冲。
- **推荐要能解释**：展示推荐理由、信息来源、更新时间和核验状态。
- **从真实起点出发**：支持住宿地、当前位置或用户指定地点作为起点和终点。
- **适配真实场景**：考虑白天/夜间、营业时间、天气、用餐时段、步行接受度和返程时间。
- **用户保留控制权**：支持收藏、替换、锁定、局部重排和保存多个方案。
- **模型不代替事实数据**：距离、耗时、营业时间和天气等事实由结构化数据或外部服务提供，并保留来源与更新时间。

## 目标用户

- 临时决定出行、没有时间逐篇整理攻略的人。
- 第一次到访某个城市，希望快速获得可执行路线的人。
- 已经订好酒店和交通，但不确定每天如何安排的人。
- 希望兼顾景点、特色美食、休息和交通效率的人。

## 核心使用流程

1. **描述出行计划**：填写城市、日期、到达/离开时间、住宿位置、同行情况、交通方式、兴趣、节奏和饮食限制。
2. **形成候选地点**：从可追溯的地点库和攻略证据中筛选景点、街区、美食、夜间活动及雨天备选。
3. **生成每日行程**：结合时间窗口、营业时间、天气、路线耗时、用餐时段和个人偏好排出顺序。
4. **查看并调整**：在时间线和地图之间切换，替换地点、改变顺序、采用备选方案或锁定已确认项目。
5. **出行中动态更新**：天气变化、临时闭店、迟到或主动改变计划时，提示受影响的安排并进行局部重排。

## 移动端功能

移动端采用四个固定底部入口，地图属于“行程”页内的视图模式，不单独占用一个 Tab。

| 入口 | 主要内容 |
| --- | --- |
| 首页 | 搜索城市与日期、开始新计划、继续最近行程、查看城市灵感 |
| 行程 | 按日期查看天气、时间线、地点、美食、交通；在时间线与地图之间切换 |
| 发现 | 浏览城市体验、路线主题、白天/夜间活动和特色美食 |
| 我的 | 管理已保存行程、收藏地点、出行偏好和账户设置 |

主要子流程包括：创建计划、生成方案、地点详情和调整行程。主流程为：

```text
首页 → 创建计划 → 生成方案 → 行程
                         ↕
                   时间线 / 地图
                         ↓
                  地点详情 / 调整行程
```

行程和地图使用同一份当天数据：切换日期时同步更新时间线、地图标记和路线；点击行程卡片可以定位地图站点，点击地图标记可以查看对应行程项。

## Web 管理后台

后台面向运营人员，不承担旅行用户的主要使用流程，主要用于维护产品可信度和内容质量：

- 攻略来源审核与证据管理。
- 地点、特色美食和营业信息维护。
- 路线方案和城市数据管理。
- AI 推荐规则与评分权重配置。
- 用户反馈、行程效果和服务状态查看。
- 关键字段变更记录、核验状态和操作日志。

地点信息应支持“待核验、已核验、冲突、过期”等状态。来源之间存在差异时，应保留差异或降低推荐置信度，不应直接把模型生成的内容当成已核实事实。

## 推荐与规划逻辑

推荐采用可解释的多维评分，评分只用于排序，不能覆盖硬约束。

主要信号包括：兴趣匹配、来源质量与信息新鲜度、昼夜和营业时段适配、天气适配、路线顺路程度、地点特色与口碑，以及预算、饮食、同行人群和步行要求。

规划层先处理用户可用时间、营业时段、出发/结束地点、锁定项目和不可重叠安排等硬约束，再以减少绕行、控制通勤时间、兼顾兴趣、多样性和休息为目标优化路线，最后由大模型生成易读的行程说明。

以下信息不能由模型自行补造：

- 具体距离和交通耗时。
- 营业时间、价格和临时闭店状态。
- 天气预报和确定性的天气承诺。
- 地点是否真实存在或是否仍可访问。

## MVP 范围

### 必须完成

- 选择城市、日期、到达/离开时间和住宿位置。
- 设置兴趣、节奏、交通方式和餐饮限制。
- 基于一个可控、可追溯的地点数据集生成一至数日行程。
- 考虑营业时间、昼夜适配、地点间路线和天气信息。
- 在地图上显示真实地点、顺序和路线。
- 支持替换地点、局部重排、锁定项目和保存计划。
- 展示推荐理由、信息来源、更新时间和不确定状态。

### 暂不纳入

- 覆盖所有城市和内容平台的自动采集。
- 机票、酒店、门票和餐厅预订支付。
- 自动处理所有临时交通事件或商户变化。
- 复杂多人协作、社交动态和旅行社区。

首版建议选择一个试点城市，先验证“从住宿起点出发，结合昼夜、天气、路线和美食生成计划”是否比用户手动搜索和拼接更省事。

## 技术方案

计划采用 TypeScript 单仓库，移动端、Web 后台和服务端共享接口类型与校验规则：

| 层次 | 计划方案 |
| --- | --- |
| 移动端 | React Native + Expo + TypeScript |
| Web 管理端 | React + Vite + TypeScript + shadcn/ui |
| 后端 API | Hono + TypeScript + Zod |
| 数据库与 ORM | MySQL 8.0+ + Prisma |
| 仓库与包管理 | pnpm workspace |
| 本地依赖 | Docker Compose |
| 外部能力 | 地图/地理编码、路线、天气和大模型适配层 |

```text
移动端 ─┐
        ├─ 应用 API 与权限层 ─ 核心服务 ─ 业务数据库与地理索引
管理后台 ┘                       └─ 地图、路线、天气、大模型适配层
```

核心数据对象包括：`Place`、`ContentEvidence`、`OpeningInfo`、`Trip`、`ItineraryItem`、`RouteLeg`、`WeatherSnapshot`、`UserPreference` 和 `RecommendationReason`。

## 开发路线

1. **需求与数据验证**：确定试点城市、地点类型、内容来源、地图/天气供应商和授权边界。
2. **产品与技术定稿**：冻结四 Tab 信息架构、行程/地图联动、后台审核流、API 契约和数据字典。
3. **MVP 开发**：打通移动端、后台、API、地点库、路线、天气和模型的端到端流程。
4. **城市试点与修正**：用真实出行场景验证晚到、雨天、返程日、锁定项目和局部重排。
5. **攻略导入与个性化**：加入链接/文本导入、地点去重、来源管理、收藏和反馈。
6. **动态旅行助手**：支持天气变化、临时闭店、行程延误、多城市和多人协作。

## 本地开发约定（规划）

正式代码仓库初始化后，建议统一使用 Node.js 24 LTS、固定版本 pnpm、Docker Desktop/Compose、Git 和团队统一的 IDE。

预计启动流程：

```bash
pnpm install
cp .env.example .env
docker compose up -d db
pnpm prisma migrate dev
pnpm prisma db seed
pnpm dev
```

环境变量只放在本地或受控的部署环境中，真实密钥不得提交到 Git。地图、天气或模型服务尚未就绪时，可以使用 mock 响应开发页面和接口，但必须明确标记为演示数据。

## 数据与内容合规

首版从一个城市、有限地点类型和可追溯来源开始。攻略内容优先来自授权数据、人工维护以及用户主动提供的文本或链接。对小红书、抖音等平台的接入方式，应以平台允许的接口、授权和数据使用条件为准，不能把未经许可的批量抓取作为产品前提。

每条关键事实都应尽量保存来源、证据、发布时间、最后核验时间和核验状态。对于远期天气、未知营业时间或来源冲突，应明确显示不确定性，并给用户出发前确认的提示。

## 项目验收重点

- 用户可以完整填写出行信息并获得按日期、时间排序的计划。
- 计划包含景点、特色美食、停留时间、交通段和弹性时间。
- 时间线与地图使用同一份数据，并能双向定位站点。
- 晚间到达、返程日和雨天场景有合理安排或备选。
- 地点详情能说明推荐理由、来源、更新时间和适合时段。
- 替换或局部重排后，已锁定项目仍被保留。
- 后台可以审核来源、维护地点与路线、配置推荐规则并追溯修改。
- 外部服务失败时，界面给出清晰降级提示，不输出虚构事实。

## 关键效果指标

- 从填写计划到获得首个可行方案所需时间。
- 行程保存或分享比例。
- 地点被保留、替换或删除的比例及原因。
- 用户对路线顺畅度、时间安排和推荐相关性的评分。
- 营业时间、地点匹配和路线信息的错误反馈率。
- 天气变化后，用户成功采用备选方案的比例。
